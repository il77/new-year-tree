## Intent

**Problem:** Сцена сейчас рисует только искру жёстко в `renderFrame`. Эпики 2–4 (гирлянда, календарь, мир) не имеют официального способа добавлять свои объекты на сцену — каждый будет лезть в `scene.js` по-своему, и части разъедутся.

**Approach:** Ввести один общий интерфейс регистрации объектов на сцене (stub + документация): объект подписывается на кадр и получает ctx/размер/время. Существующее поведение страницы не меняется — искра продолжает рисоваться как сейчас.

## Boundaries & Constraints

**Always:** интерфейс один на все эпики и документируется там, где его найдёт эпик 2–4; существующие 7 тестов и видимое поведение страницы не меняются; по-прежнему ноль зависимостей (node:test).

**Never:** никаких реальных объектов гирлянды/календаря/мира (scope эпиков 2–4), никакой анимации (story 1.5), никакого ритуала (story 1.3). Документация контракта не превращается в общее описание проекта.

## Implementation Notes

- Контракт — фабрика `createSceneContract()` (изолированное состояние в замыкании) плюс общий `sceneContract` для страницы; регистрация сортируется по слою, при равенстве — по порядку вызова.
- `register` проверяет аргументы и бросает `TypeError` с сообщением `register:`; невалидные значения не попадают в список.
- Вне браузера `page === null`, общий экземпляр тестами не засорён; эпики 2–4 получают `{ render, contract, ritual }` через `bootstrap`.

## Design Notes

Форма контракта — на усмотрение агента; главное: без глобального мутабельного состояния, ломающего тестируемость (в духе `bootstrap(doc, win)`: состояние в замыкании/factory, а не в модульном singleton, если это не помешает простоте). Порядок отрисовки должен разрешить слои эпика 4 (фон → ёлка → огоньки → слои мира) без знания их содержимого — регистрация с явным порядком/слоем достаточна.
